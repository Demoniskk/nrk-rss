# nrk-podcast-rss

Standard podcast RSS feeds for every podcast on NRK Radio, generated by a small
Go program and published as a static site on GitHub Pages.

NRK Radio has no public RSS feeds you can paste into a normal podcast app. This
reads NRK's public JSON API, builds a conventional RSS 2.0 + iTunes feed per
podcast, and publishes one `.xml` file each.

---

## How it works

One binary, three commands:

| Command | What it does | When |
| --- | --- | --- |
| `scrape-all` | Pages through **every episode** of every podcast. | Once, to seed the database. |
| `update` | Fetches **only episodes not already stored**. | Daily, from Actions. |
| `export` | Rebuilds the site from the database. No NRK calls. | After template changes. |

### The update/scrape split

Building one episode's `<item>` costs three API calls: the episode metadata
(free, it comes with the episode list), a playback-manifest lookup for the audio
URL, and a `HEAD` on that URL for the enclosure's size and type.

Published episodes never change, so re-fetching them daily would be pure waste —
one podcast in this catalogue has over 800 episodes. So a SQLite database at
`state/episodes.db` stores everything needed to re-render an episode's `<item>`
offline. `update` asks NRK for the newest page of episodes, stops at the first
episode ID it already has, and fetches only what came before it.

A quiet day costs about three requests per podcast and finishes in seconds. A
full backfill is tens of thousands of requests and takes hours.

### The database is committed to the repo

`state/episodes.db` is checked in deliberately. A lost Actions cache would
silently re-do work, but a lost database with nothing to fall back on would
silently *skip* episodes — `update` would have nothing to diff against. So the
state is committed rather than cached. Its WAL sidecar files are gitignored.

### Pipeline

```
NRK JSON API  ──▶  internal/nrkapi   client, rate limiting, retries
                        │
                        ▼
                   internal/scrape   diff against stored IDs, fetch the rest
                        │
                        ▼
                   internal/store    SQLite: state/episodes.db
                        │
                        ▼
          internal/feed + internal/site
                        │
                        ▼
   docs/feeds/*.xml · docs/index.html · docs/feeds.json  ──▶  GitHub Pages
```

### Output

- `docs/feeds/<podcast_id>.xml` — one RSS feed per podcast.
- `docs/index.html` — a search box, an overview of every podcast, and a link to
  each RSS feed.
- `docs/feeds.json` — machine-readable manifest, including any podcasts that
  failed the last run and why.

Feeds are RSS 2.0 + iTunes, plus `<podcast:season>` and — with `--rich` —
`<podcast:person>` and inline Podlove chapter markers. XML comes from
`encoding/xml`, so `&`, `<` and quotes in titles are escaped properly.

### Automation

- `.github/workflows/scrape-all.yml` — manual (`workflow_dispatch`) only. Run
  this once to seed the database.
- `.github/workflows/update.yml` — daily at 03:17 UTC, plus a manual trigger.
  Runs the tests, runs `update`, commits `state/episodes.db` and `docs/` only if
  something changed, then deploys to Pages via `upload-pages-artifact` +
  `deploy-pages`.

Enable Pages with **Settings → Pages → Source: GitHub Actions**.

### Running it locally

```bash
go build -o nrk-podcast-rss ./cmd/nrk-podcast-rss

./nrk-podcast-rss scrape-all --only desken_brenner,abels_taarn   # try a couple
./nrk-podcast-rss scrape-all                                     # the lot (slow)
./nrk-podcast-rss update                                         # incremental
./nrk-podcast-rss export                                         # rebuild site
```

`-h` on any command lists its flags. The ones that matter: `--rate` (requests
per second, default 4), `--concurrency` (podcasts at once, default 5),
`--max-duration` (stop cleanly after e.g. `5h`), `--only`, `--force`.

## Findings along the way

The interesting parts of this build were all things the API documentation
doesn't tell you.

### NRK rate-limits hard, and punishes you for arguing

The first realistic run failed **11 of 14 podcasts** with HTTP 429. Measuring
the live API:

- A 429 comes back with `Retry-After: 600` — ten minutes.
- The penalty **persists while requests keep arriving**. Probing at a mere
  1 req/s *during* a penalty window still returned 429 about half the time.
  After 600 seconds of complete silence, 15 consecutive requests at 1 req/s all
  succeeded.
- Once clear, 3 req/s over 90 requests and 5 req/s over 50 requests were both
  clean.

So the limiter isn't a simple token bucket you can nibble at — continuing to
send is what keeps you locked out.

The fix that actually mattered: **a 429 pauses every worker, not just the one
that received it** (`internal/nrkapi/throttle.go`). Backing off a single
goroutine while nineteen others keep hammering is precisely what keeps the
penalty alive. Alongside that, all requests share one rate limiter (4 req/s for
the API; audio `HEAD`s get their own budget since they hit a different host), so
concurrency controls parallelism rather than request rate. The same 14 podcasts
then completed with zero failures.

### A CI timeout would have silently destroyed the backfill

At a polite request rate, `scrape-all` takes longer than GitHub's six-hour job
limit. The trap: when GitHub kills a job at its timeout, **subsequent steps
never run** — so the commit step never fires and the entire backfill is lost
with nothing to show for it.

Hence `--max-duration`: the scraper stops itself at 300 minutes, exits zero, and
the commit step still runs. Since a run skips episodes already stored, simply
re-running the workflow continues from where the last one stopped. Verified: a
budget-truncated run exits 0 with partial state committed, and re-running
resumed 11 → 52 episodes without re-fetching anything.

### Making "no empty commits" actually true

The workflow is supposed to skip committing when nothing changed. Naively it
never would have, because two things churned on every single run:

- `lastBuildDate` in each feed, and `generated_at` in `feeds.json`.
- `last_scraped` in the podcasts table, which rewrote the committed database.

So `lastBuildDate` is now derived from the newest episode rather than the run
time; `feeds.json` is left untouched when `generated_at` is the *only*
difference; and the podcast upsert is conditional on something having actually
changed. A no-op run now leaves every file **and the database itself**
byte-identical.

### Two API details that differ from the obvious reading

- The search endpoint (`/radio/search/categories/podcast`) serialises image
  locations as `uri`. Every catalog endpoint uses `url`. Both are handled.
- `indexPoints` (chapters) and `contributors` (credits) appear **only** on the
  single-episode endpoint — never in the episode list, despite the list
  otherwise returning the same shape. Chapters and credits therefore genuinely
  cost a fourth call per episode, which is why they sit behind `--rich` instead
  of being on by default.

Also worth knowing: the catalogue mixes in entries of type `customSeason`
(362 of them versus 235 real podcasts at time of writing). Those are slices of
other series, not podcasts, and are filtered out.

### A page cap that would have left permanent holes

`update` stops at the first episode it already knows, with
`--max-pages-per-podcast` as a safety cap for a podcast that deleted and
re-added its whole catalogue.

But applying that cap to a podcast with *nothing* stored yet would be a quiet
bug: it would fetch only the newest few pages, and every later run would stop at
the newest episode it already had and never look further back — a permanent hole
no amount of re-running would fill. So the cap deliberately doesn't apply to
podcasts new to the database. They get backfilled in full, which means new
podcasts appearing on NRK are picked up completely by the daily job without
another `scrape-all`.

### Smaller ones

- NRK's manifests report `audio/mp3`, which isn't a registered MIME type. The
  `HEAD` response gives the correct `audio/mpeg`, so the served type wins.
- Episode audio URLs redirect to a CDN. The feeds keep the stable
  `podkast.nrk.no` URL rather than the redirect target.
- `podcast:season` requires a numeric value, but NRK season IDs are sometimes
  slugs like `11-september`. The tag is skipped rather than emitted invalid.
- SQLite's `NOCASE` collation only folds ASCII, so "Podkast To" sorts before
  "Podkast Én". This broke a test that assumed otherwise — worth knowing before
  relying on `ORDER BY title COLLATE NOCASE` for non-English titles.

## Layout

```
cmd/nrk-podcast-rss/   CLI entry point
internal/nrkapi/       HTTP client, rate limiting, retries
internal/store/        SQLite state store
internal/scrape/       discovery, diffing, fetching
internal/feed/         RSS/iTunes XML generation
internal/site/         index.html and feeds.json
```

Pure-Go SQLite (`modernc.org/sqlite`), so CI cross-compiles without cgo.
`go test ./...` covers the API client, the state store, feed rendering, the site
export, and the scrape logic — including request-count assertions that pin down
exactly how much work `update` is allowed to do.

## Scope

This publishes NRK's own publicly listed episode metadata and links to the audio
files NRK already serves publicly. No audio is downloaded, re-hosted or
modified.
